# Bounded A100 lifecycle qualification

Executed on basilisk with the real Unix-socket GPU broker and the protocol-pinned `vllm/vllm-openai@sha256:770fe65b2c73ee74a5c42165cf3433de4048cc2cd9c57a937ca4e35aba5aa87b` image. Requested a scoped 1024 MiB lease on GPU UUID `GPU-170a99ee-850f-2182-1050-4e8d3c87b6b0`; no benchmark or model inference ran.

The container allocated and filled a 256 MiB torch CUDA tensor, synchronized CUDA, wrote the lease-digest readiness marker and held the allocation. The success attempt exited after five seconds; the crash attempt held for 300 seconds and its supervisor received SIGKILL immediately after readiness. Before supervisor loss, NVIDIA process telemetry reported **748 MiB** for owned host PID **1608543** (tensor plus CUDA context). A fresh controller acquired the abandoned record lock, identified the labeled container and its CUDA process, stopped the container, verified the process/cgroup allocation absent, released only the recorded lease and removed the stopped container. Both receipts have cleanup complete; the crash receipt retains the owned CUDA PID and ordered verification/release timestamps.

Private original records are under `/srv/matric-eval/results/issue156-lifecycle-qualification/`. Only sanitized `record.json` was copied here; token files and readiness filenames were not copied. No unrelated allocation was stopped or included in these receipts. The broker accepted both small allocations. The second attempt's successful acquisition also verifies the first lease did not strand the next attempt.

Reproduction drivers for this execution are retained on the host in `/srv/matric-eval/workspaces/matric-eval-156-lifecycle/matric156-qualify.py` and `matric156-crash.py`. This qualification proves real success and supervisor-loss cleanup, not a host reboot or full expensive-model pipeline. Unit fixtures separately cover outage/reconnect, lost acquire acknowledgment, scope/owner mismatch and remaining CUDA memory.

The third receipt, `cuda-preflight-integrated.json`, qualifies the integrated controller after the staged admission gate was wired. Before acquisition, its checks verified the broker socket, effective root/write context and actual broker status response. The resident check then queried Docker's labeled container PID and independently required that PID in NVIDIA CUDA process telemetry. It admitted the real tensor workload and completed ordered cleanup. The launch command/GPU/run/attempt binding and preflight fingerprint are in the public record; detailed private stage receipts remain next to the original record. Driver: `matric156-integrated.py` in the same dedicated host workspace. These are explicitly bounded lifecycle probes, not substitutes for each benchmark's own preflight profile.
